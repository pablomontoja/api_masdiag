# Framework Defaults Decisions

**Feature**: 009-rails-80-upgrade | **Tasks**: T040–T042 | **Date**: 2026-08-18

`config.load_defaults` raised **7.2 → 8.0** in `config/application.rb`. FR-019 requires each default
that changes behaviour be recorded with its decision and reason.

## Adopted

| Default | New value | Decision | Reason |
|---|---|---|---|
| `Regexp.timeout` | `1.0` | **Adopt** | ReDoS protection. All 6 regex sites verified — see below |
| `active_support.to_time_preserves_timezone` | `:zone` | **Adopt** | Set by `load_defaults 8.0`. Adopting it *removed* a deprecation warning that appeared at boot immediately after the bump |
| `action_dispatch.strict_freshness` | `true` | **Adopt** | Prefers `If-None-Match` over `If-Modified-Since` per RFC 7232 §6. The API sets no conditional-request headers; no measured behaviour changed |
| Schema dump column ordering | alphabetical | **Adopt, unexercised** | `db/schema.rb` is not regenerated (FR-020). Verified identical to the baseline snapshot both before and after adoption |
| Remaining 8.0 defaults | various | **Adopt** | Full suite (758 examples) and all 11 namespaces verified after adoption, with zero assertions modified |


Kept in place as a marker for the next upgrade. It is inert.

## The one that needed real work: `enqueue_after_transaction_commit`

**Planning was wrong about the mechanism, and the measurement proved it.**

The plan (FR-014) called for setting `config.active_job.enqueue_after_transaction_commit`
explicitly in `application.rb`. Reading `activejob-8.0.5.1/lib/active_job/railtie.rb:28-53` shows
why that does not work:

1. The global config is **deprecated in 8.0 and removed in 8.1**. Setting it emits a deprecation
   warning telling you not to.
2. It accepts only `:always` / `:never`. Anything else — including the `:default` the plan
   specified — falls through `else` and maps to **`false`**.
3. Rails' own guidance: *"due the nature of this behavior, it is not recommended to be set
   globally"*. The supported mechanism is per-job `self.enqueue_after_transaction_commit=`.

### What was measured

Under `load_defaults 7.2`, before any change:

```
ActiveJob::Base.enqueue_after_transaction_commit => false
ROLLBACK -> enqueued 1 job    ← the partner would have been notified
COMMIT   -> enqueued 1 job
```

**The framework-level guard was never active.** Protection rested entirely on spec 007's code-level
fix — enqueuing after the transaction block closes in `Fv1::KitController` — and on the SolidQueue
adapter. That is one layer, not the two the plan assumed.

Setting the global config to `:default` changed nothing (it maps to `false`). Setting it at runtime
changed nothing either; the value is read when the adapter is configured at boot.

### What was done

Declared on the two jobs that POST to an external partner and retry on failure:

- `app/jobs/lalen_api/assign_kit_tests_job.rb` — the job spec 007 was written to protect
- `app/jobs/lalen_api/register_kit_job.rb`

```ruby
self.enqueue_after_transaction_commit = true
```

### Verified after

```
global default:    false
AssignKitTestsJob: true
RegisterKitJob:    true
ROLLBACK -> enqueued 0    (expect 0)  ✅
COMMIT   -> enqueued 1    (expect 1)  ✅
```

The guarantee is now genuinely two-layered, attached to the jobs that need it, in the mechanism
Rails 8.1 will keep. This satisfies the constitution's requirement (Development Workflow item 4)
that ordering-critical enqueue intent "survive a defaults change" — better than the global setting
would have, since that one disappears entirely in 8.1.

**Note**: this is the one place the upgrade modified application code, against the plan's expectation
(invariant I6). It is justified and recorded: the alternative was leaving a partner-notification
guarantee resting on a single layer while believing it had two.

## Regex sites under `Regexp.timeout = 1.0` (T048, T049)

| Site | Input source | Result |
|---|---|---|
| `LalenApi::RegisterKit::EMAIL_REGEXP` | **External partner** | 7 cases, **0 timeouts**, all < 0.02 ms |
| `Masdiag::ReservedSampleCodesCreator:43` `/[oO0]/i` | Internal | Character class; no backtracking |
| `V1::KitController:105,106` `/[oO0]/i` | Internal | Same |
| `MasdiagMailer::SendCancellationNotificationsJob:62,71` `/\A\d+\Z/` | Internal | Anchored digits; no risk |

The email validator was exercised with valid, short-valid, invalid, empty, 300-char local part,
300-char domain, and a deliberately ReDoS-shaped input (`a{60}@a{60}.a{60}!`). Slowest was 0.018 ms
against a 1000 ms budget. The bounded quantifiers (`{0,61}`) resist catastrophic backtracking, as
research R7 predicted — now demonstrated rather than assumed.
